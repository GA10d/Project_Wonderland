# 像素游戏：Tilemap 地形与建筑、装饰物搭建

适用范围：以俯视或斜俯视、正交网格的 2D 像素游戏为主。横版、等距地图可复用数据分层和邻接规则，但需要调整坐标、碰撞及排序方式。整理日期：2026-09-10。

这里讨论的是通用实现方式；引擎功能引用官方文档，数据结构与实现流程是本文给出的设计建议，并非对某一款游戏内部实现的断言。

## 1. 先理解整体流程

**先决定每格是什么地形，再根据邻居选择贴图，最后把具有独立占地和行为的对象放上去。**

```text
手绘 / 程序生成
       ↓
逻辑地形网格：草地、水、沙地、高度……
       ↓
邻接匹配：边、外凸角、内凹角、中心……
       ↓
地形 Tilemap：每格引用 tileset 中的一张图
       ↓
建筑选址 → 入口与道路 → 树木、大石 → 小装饰
       ↓
碰撞 / 寻路 / 交互 / 前后遮挡
```

Tile 是一块图像及其相关配置；tileset 是图块集合，常打包在一张图集里；tilemap 是各格引用哪个图块的地图。图集里的排列次序并不自带“这是左上角”的含义，需要规则或元数据告诉系统。

地形生成和自动拼接是两个问题：噪声、手绘、多边形填充等负责决定哪里有陆地；autotiling 负责让已经确定的陆地边缘接起来。自动拼接本身不保证岛屿好看、道路可达或房屋选址合理。

## 2. 怎么处理中心、边与角

### 2.1 九宫格能解决规则矩形

假设要画一块矩形草坪：

```text
┌─────┬─────┬─────┬─────┐
│左上角│ 上边 │ 上边 │右上角│
├─────┼─────┼─────┼─────┤
│ 左边 │ 中心 │ 中心 │ 右边 │
├─────┼─────┼─────┼─────┤
│左下角│ 下边 │ 下边 │右下角│
└─────┴─────┴─────┴─────┘
```

四个外角、四种边和一个中心，共九种基本图块，可以铺出宽高至少两格的矩形。单格、单行和单列还可能需要独立素材。

不规则地形还会出现内凹角、细长连接、孤立格、孔洞，以及一格里多个角同时露出的情况，所以不能只准备这九张。

### 2.2 四邻域：16 种连接状态

先只检查当前格的上、右、下、左是不是可连接的同类地形：

```text
       N=1
 W=8   当前格   E=2
       S=4

mask = N×1 + E×2 + S×4 + W×8
```

这里 N/E/S/W 为布尔值。例如 `E=1, S=1`，其他为 0，则 mask=6；对实心区域而言可对应左上外角。mask=14 表示右、下、左都连接，是上边；mask=15 表示四边都连接。

四个布尔值共有 `2⁴=16` 种状态。道路、管道、栅栏等主要关心四向连通性的对象很适合这种规则。但四边都连接不代表四个角也被填满。

### 2.3 八邻域：区分外凸角和内凹角

```text
NW   N   NE
 W   C    E
SW   S   SE
```

以当前格 C 的左上角为例：

| N | W | NW | 左上区域的含义 |
|---|---|---|---|
| 0 | 0 | 任意 | 外凸角，向上和向左都露出边界 |
| 1 | 0 | 任意 | 左侧露边 |
| 0 | 1 | 任意 | 上侧露边 |
| 1 | 1 | 0 | **内凹角**：上、左相连，左上留空 |
| 1 | 1 | 1 | 该角内部连续 |

这是一个角的判断，一张 tile 最终要综合四个角。以下 `#` 为草地，`.` 为背景，`C` 是正在判断的草地格：

```text
外凸左上角         内凹左上角
...                .##
.C#                #C#
.##                ###
```

第二种情况若仅按四邻域选中心图，就会把左上的缺口画错。注意：**内凹角贴在 C 这样的边界地形格上，不是简单在空格里补一张外角图。**

### 2.4 为什么常说 47-tile Blob

八个邻居原本有 `2⁸=256` 种状态。常用 Blob 规则只在相邻两条直边都连接时，才考虑它们之间的对角邻居：

```python
NW = NW and N and W
NE = NE and N and E
SE = SE and S and E
SW = SW and S and W
```

归一化后只有 **47 种不同连接形态**。数字 47 不是所有自动拼接方案的固定要求，也不是任意地形过渡都只需要 47 张图。它针对这种二值区域边界规则，且不计美术变体；图块复用、旋转和子块组合也会改变实际素材数量。

Tiled 官方文档将 Terrain Set 分为角匹配、边匹配和混合匹配，并说明混合匹配可以使用缩减的 47-tile Blob 集合。[来源：Tiled 地形系统](https://doc.mapeditor.org/en/stable/manual/terrain/)

另一种实现是把一格拆成四个小象限，根据各自邻接状态拼图。它可以减少原画重复，但前提是素材本身按子块方式设计，不能把任意 tileset 直接切开就期待正确拼接。

### 2.5 从 mask 到实际贴图

建议保存两类数据：

```text
terrain[y][x] = "grass"              # 逻辑地形
visual[y][x] = resolve(grass, mask)   # 由逻辑地形派生的图块引用
```

解析过程：

1. 读取当前格的地形和八个邻居。
2. 判断哪些邻居允许连接；可能按 terrain ID，也可能按连接组判断。
3. 归一化对角关系，计算 mask。
4. 查找 `terrain + mask → 图集坐标或 tile ID`。
5. 若同一形态有多张图，再挑选纹理变体。

**mask 的数值不是图集索引。** 每套素材的排布可能不同，需要手工标注或用编辑器配置映射表。本文示例使用 `N,E,S,W,NE,SE,SW,NW` 的位序；其他工具可能完全不同。

随机变体建议由世界 seed、坐标、地形类别共同决定。否则每次刷新边缘都会让草纹重新随机，产生闪变。含有固定光照方向的素材也不宜随意旋转。

### 2.6 多种地形、高度与局部刷新

草对水、草对沙、草对泥的边缘未必相同，单纯判断“是不是草”会丢失背景信息。可以选用以下实现：

| 方法 | 用法与限制 |
|---|---|
| 分层覆盖 | 底层完整铺水/泥，上面画带透明边缘的草地；简单，但要明确谁覆盖谁 |
| 成对过渡 | 配置草—沙、沙—水等组合；三种地形交汇需要特殊规则或缓冲带 |
| 边/角标签匹配 | 每条边或每个角标记地形类型；自动选择可与邻块匹配的图块 |

不要把两套系统混为一谈：格中心存地形、再计算邻居 mask，与在 tile 的边/角上存地形标签，是不同的数据约定。

悬崖还需要高度或平台层级。应区分顶面、崖壁、崖脚、台阶与可通行连接，不能仅靠“颜色不同”推断地形高度。

对固定八邻域解析器，修改一格后只需重新解析它及周围八格；批量修改时将脏区域向外扩一格。跨 chunk 时也要读取相邻 chunk 的边界数据。道路宽度修补、多格悬崖和会传播的约束算法，更新范围可能更大。

## 3. 地形上怎么放建筑与装饰

### 3.1 根据用途选择表示方式

| 内容 | 常用表示 | 原因 |
|---|---|---|
| 草地、水面、道路 | Tilemap | 大面积铺设、邻接更新 |
| 小花、碎石、地面纹理 | 装饰 Tilemap 或实例 | 通常不影响遮挡与碰撞 |
| 树、石头、箱子 | 独立对象 / prefab / scene | 有独立碰撞、排序或交互 |
| 固定房屋 | 对象或多层图块模板 | 可以一整张画，也可以由多格组成 |
| 可变大小建筑 | 模块化图块加建筑逻辑对象 | 墙、门、屋顶可组合，状态仍需统一管理 |

“建筑由 tile 组成”和“建筑是一个逻辑对象”可以同时成立。例如一栋房子渲染时用了 30 块图，存档中仍是一条带唯一 ID、类型、位置和状态的建筑记录。

Tiled 的 Object Layer 可记录位置、形状、tile 对象及自定义属性；导入游戏时再由游戏代码解释成建筑、出生点或交互对象。[来源：Tiled 对象](https://doc.mapeditor.org/en/stable/manual/objects/)

### 3.2 分清四个空间概念

**贴图范围、建造占地、碰撞区域、通行预留区要分别定义。**

以一棵树为例：

```text
       ┌─────────┐
       │   树冠   │ ← 美术显示范围，允许盖住地面和角色
       │    │    │
       └────┼────┘
            ●       ← 接地锚点，也是排序参考点
           [■]      ← 树干附近的占地 / 碰撞
```

一栋房子可能有 4×3 格建造占地、4×5 格视觉范围，以及更精细的墙体碰撞。门前还要留一条不属于房屋主体的通路。树冠相交是否允许，是美术和玩法规则；不应默认等于碰撞。

推荐对象定义包含：

```json
{
  "type": "cottage_a",
  "footprintCells": [[0,0],[1,0],[2,0],[3,0], [0,1],[1,1],[2,1],[3,1], [0,2],[1,2],[2,2],[3,2]],
  "allowedTerrain": ["grass", "dirt"],
  "requiresFlatGround": true,
  "entranceCell": [1,3],
  "reservedAccessCells": [[1,3],[1,4]],
  "visualSizePx": [64,80],
  "spriteAnchorPx": [32,80],
  "worldAnchorFromOriginPx": [32,48],
  "collisionProfile": "cottage_walls",
  "renderMode": "ground_anchor_y"
}
```

这里假设格子为 16×16，局部格坐标从占地左上角起算，x 向右、y 向下。图像坐标从图片左上起算；世界锚点在占地底边中心：

```text
worldAnchor = gridOriginPx + worldAnchorFromOriginPx
spriteTopLeft = worldAnchor - spriteAnchorPx
```

因此图片比占地向上多出 32 像素。`collisionProfile` 是另行定义的碰撞配置引用，不能凭名字自动生成墙体。

### 3.3 放置判定的实际顺序

对候选建筑位置：

1. 将 footprint 的局部坐标转换成地图坐标，检查全部在边界内。
2. 检查全部占地的地形合法、高度一致；必要时检查坡度和离岸距离。
3. 检查占地不与其他对象、保护区或通路预留区冲突。
4. 检查入口和门前预留区有效，没有被堵住。
5. 根据玩法执行寻路检查，确认入口连接道路或玩家活动区。
6. 全部通过后一次性登记占地、通路预留和对象实例，并更新碰撞、寻路。

仅“门口那一格没东西”不能证明玩家走得到那里。对需要保证可达性的建筑，应从入口做 flood fill / BFS，或连到已有道路网络。障碍物放下后，还要检查是否切断必要的旧路线。

对象旋转时，除了贴图，还要一起变换 footprint、入口、碰撞和锚点。像素建筑常具有明确朝向和光照，不一定支持任意旋转。

### 3.4 推荐摆放顺序

```text
地形与高度
  → 保留出生点、重要地点、主通行区域
  → 建筑占地与入口
  → 连接入口的道路
  → 树、巨石等大物件
  → 灌木、花、碎石等小装饰
  → 最终通达性与重叠检查
```

如果城镇先有道路规划，也可以先定路再放房子；关键是建筑入口与道路共同设计，大件先确定，再填小件。

程序化散布装饰时，可以把地形类别、离岸距离、离路距离、局部密度作为候选权重。树适合形成有疏有密的小群落；石头可以偏向山脚；路边要留出角色活动空间。带最小间距的拒绝采样可以避免均匀随机产生大量重叠，但需限制尝试次数，放不下时跳过或回退。

应明确区分“无碰撞的地表纹理”和“影响通路的障碍物”，后者必须参与占地与路径验证。

## 4. 建筑、树和角色的前后关系

### 4.1 基本绘制层级

```text
较早绘制：基础地面 → 地表覆盖 / 道路 → 地面装饰与阴影
同一深度体系：角色、树干、房屋主体等按接地位置排序
较晚绘制：明确要求遮盖的前景、特效、UI
```

在屏幕 y 向下增长的俯视场景中，同一排序组里通常先画接地点 y 较小的对象，再画较大的对象。角色在树后时树遮角色；走到树前时角色遮树。排序依据应是脚底、树根等接地点，而不是图片顶部或图片中心。

固定层级优先于同层 Y 排序：如果所有树被放进永久高于角色的层，角色走到树前仍会被遮挡。Godot 提供 Y Sort 和 tile 的 Y Sort Origin 等控制项；地形连接则可使用 TileMapLayer 的 Terrain Connect/Path 工作流。[来源：Godot Tilemap](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilemaps.html)

### 4.2 大建筑不能总靠一个 Y 值

简单房屋可以按整体接地点排序。但可进入建筑、长墙、拱门、桥梁或跨度很大的对象，单个排序点往往不足以表达空间关系。

可以按需求拆成地基、墙体、屋顶、门廊等部分；屋顶在角色进入时隐藏或淡化；前景墙使用局部遮挡逻辑。树冠是否独立成层也取决于玩法，不能统一设成“永远压住角色”。

渲染遮挡、物理碰撞和寻路阻挡是三个不同系统。玩家被屋檐遮住，不代表屋檐下方一定禁止行走。

## 5. 素材准备与现成工具

拿到一张 tileset 图之后，先检查这些问题：

| 检查项 | 为什么要查 |
|---|---|
| tile 尺寸、图集边距和间隔 | 决定切图坐标是否正确 |
| 内凹角、孤立格、窄通道是否齐全 | 决定能支持哪些地形形状 |
| 是否为完整 tile 或四分之一子块 | 决定拼接算法 |
| 边缘是透明还是画死了背景 | 决定能否叠在任意底层上 |
| 是否有固定光照方向 | 决定能否旋转或镜像 |
| 建筑锚点、占地、门口定义 | 决定能否正确落地和通行 |
| 许可条款 | 决定能否用于目标项目及如何署名 |

像素素材通常需要最近邻采样；图集还需考虑 padding / extrusion、相机缩放与像素对齐，避免接缝和邻图渗色。

不必从头实现所有编辑器功能：

| 环境 | 对应功能 | 要自己提供的东西 |
|---|---|---|
| Tiled | Terrain Sets；复杂多层规则可研究 Automapping | 地形标注、规则与运行时对象导入 |
| Godot | TileSet terrain 配置 + TileMapLayer；对象用 scene | 地形组合、碰撞、对象占地与玩法 |
| Unity | 2D Tilemap Extras 的 Rule Tile；对象用 prefab | 邻居规则、输出 sprite、建造和排序逻辑 |

Godot 的地形匹配需要配置对应 terrain peering bits；Unity Rule Tile 则通过邻居条件选择输出。工具可以执行规则，但不会凭普通 PNG 自动理解全部语义。[Godot TileSet 配置](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilesets.html) · [Unity Rule Tile（3.0 文档）](https://docs.unity3d.com/Packages/com.unity.2d.tilemap.extras@3.0/manual/RuleTile.html) · [Tiled Automapping](https://doc.mapeditor.org/en/latest/manual/automapping/)

## 6. 这个项目可以怎样从最小版本开始

建议先做一个明确受限的原型：

1. 一层水背景、一种草地、固定八邻域 Blob 解析器。
2. 从 tileset 建立完整 mask 映射；缺图时显式报错或显示占位，不静默乱配。
3. 一棵树、一块石头、一栋房子，分别定义占地和视觉锚点。
4. 实现放置预览、占地检查、碰撞、接地点 Y 排序。
5. 加入口与通路预留，再加道路和有约束的装饰散布。
6. 最后加入多地形、高差、建筑拆分和 chunk 更新。

附带的 [tilemap_example.py](./tilemap_example.py) 使用 Python 标准库，演示八邻域 mask、47 种形态的枚举，以及占地/入口预留的放置检查：

```bash
python3 lectotype/tilemap_example.py
```

它是数据逻辑示例，不包含图片渲染、图集映射、碰撞引擎或寻路；其中的 `mask` 必须通过你自己的素材映射表才会变成实际 tile。

验收时至少画一次：矩形、L 形、带孔地块、单格、单格宽通道、仅对角相邻两格、跨地图边界修改；再让角色从树和房子的前后经过，并尝试在门前放石头。它们能较快暴露规则缺失与遮挡问题。
